# Exploration: appointment-role-null-hardening

## Current State

`users.role` is nullable at every layer that could enforce it:

- DB: `backend/src/main/resources/db/migration/V1__create_initial_schema.sql:10` — `role ENUM('ADMIN','DENTIST','PATIENT')`, no `NOT NULL`. This is the only migration in the repo (`V1` only) — no later migration tightens it, no seed `INSERT INTO users` statements exist in SQL (all seeding is Java-side).
- Entity: `backend/src/main/java/com/dh/dentalClinicMVC/entity/User.java:40` — `@Enumerated(EnumType.STRING) private Role role;`, no `nullable = false`.
- `Role.java` is a closed 3-value enum (`ADMIN`, `DENTIST`, `PATIENT`), no mechanism for a 4th value to appear at runtime — the "future enum value" framing from the prior exploration is not a real risk, only "null" is.

Two independent failure modes on a hypothetical null-role row, both still present, verified against current line numbers post `appointment-collection-mapping`:

1. **Filter-layer NPE** — `User.getAuthorities()` (`User.java:44-46`) does `List.of(new SimpleGrantedAuthority("ROLE_" + role.name()))`, NPEs on `role.name()` if role is null. Called from `JwtAuthenticationFilter.doFilterInternal()` (`JwtAuthenticationFilter.java:35-110`) at line 77, inside the `try` block (lines 60-107) but outside both catches: `catch (UsernameNotFoundException ex)` (line 88, for stale-principal / missing row) and `catch (JwtException | IllegalArgumentException ex)` (line 100, for malformed/expired tokens). Neither `NullPointerException` supertype matches those catch types, so it propagates uncaught out of the filter. Filters run before `DispatcherServlet`, so `GlobalExceptionHandler`'s `@ControllerAdvice` can't intercept it either — it surfaces as a bare 500 for every authenticated request by that user, not just appointment listing.
2. **`findAllForCurrentUser()` privilege-fallthrough** — `AppointmentServiceImpl.java:205-222` (post-refactor, unchanged dispatch logic, only mapping calls changed): `if (role == Role.PATIENT) ... else if (role == Role.DENTIST) ... else { appointments = appointmentRepository.findAll(); }` (ADMIN comment at line 217). A null role falls into the `else` and gets full global appointment access, silently equivalent to ADMIN.

Existing 401 machinery (from `stale-principal-resolution`, already shipped): `StalePrincipalException` (`exception/StalePrincipalException.java`) is a plain unchecked `RuntimeException` caught by `GlobalExceptionHandler.handleStalePrincipal()` (`GlobalExceptionHandler.java:231-242`) → 401 `ErrorResponse` with `error: "No autenticado"`. At the filter layer, `UsernameNotFoundException` thrown by `userDetailsService.loadUserByUsername()` is caught (log only, no response write) and the request falls through to `filterChain.doFilter()` unauthenticated; `StalePrincipalEntryPoint` (`security/StalePrincipalEntryPoint.java`, wired in `SecurityConfiguration.java:64`) then produces the actual 401 body for any `authenticated()` route the unauthenticated request still can't pass. This is a different mechanism than `StalePrincipalException` — one is a controller/service-layer thrown-and-caught exception, the other is filter-layer "leave unauthenticated, let the custom `AuthenticationEntryPoint` write the 401." A null-role condition on an existing row is neither: the row IS found (`loadUserByUsername` succeeds), so `UsernameNotFoundException` never fires; and it's not a controller-layer missing-row lookup, so `StalePrincipalException` never fires either. Today it hits neither path — it NPEs before either mechanism can engage.

**Critical wiring discovery not in the prior exploration**: `ApplicationConfig.java:23-32` defines a single shared `UserDetailsService` bean (a lambda: `userRepository.findByEmail(username).orElseThrow(() -> new UsernameNotFoundException(...))`) used by both `JwtAuthenticationFilter` (via `loadUserByUsername` at `JwtAuthenticationFilter.java:68`) and `DaoAuthenticationProvider` (`ApplicationConfig.java:37-44`, used by `AuthenticationService.login()`'s `authenticationManager.authenticate()` call). Any fix that adds a null-role check inside this lambda affects the login path too, not just the JWT-filter path: `DaoAuthenticationProvider` normally translates `UsernameNotFoundException` into `BadCredentialsException` (Spring Security's default user-enumeration hiding behavior), which `GlobalExceptionHandler.handleBadCredentials()` already maps to 401 "Credenciales inválidas" — a plausible-but-message-misleading existing 401 path for login, distinct from the `StalePrincipalException`/`StalePrincipalEntryPoint` machinery. This tri-path branching (JWT filter vs. login vs. downstream service dispatch) is the central design question for the proposal phase.

## How a Null Role Could Arise in Practice (Reachability Assessment)

Every current write path to `users.role` was checked and all of them defensively default a null role rather than persist it:

- `PatientServiceImpl.save()` (`PatientServiceImpl.java:55-57`): `if (patient.getRole() == null) patient.setRole(Role.PATIENT);`
- `PatientServiceImpl.update()` (`PatientServiceImpl.java:91-95`): defends against both null and client-supplied `ADMIN`.
- `DentistServiceImpl.save()`/`update()` (`DentistServiceImpl.java:52-54, 87-91`): identical pattern, defaults to `DENTIST`.
- `AuthenticationService.createPatient()` (`AuthenticationService.java:91`): unconditionally sets `Role.PATIENT`.
- `AuthenticationService.register()` (`AuthenticationService.java:44`): `Role requested = request.getRole() == null ? Role.PATIENT : request.getRole();` then rejects anything but `PATIENT`.
- `DataInitializer.java` and `E2eDataInitializer.java` (dev/e2e fixtures, not production paths): all explicit role sets, no gaps.
- No SQL seed data exists (`V1` has no `INSERT INTO users` statements), and no other code path calls `IUserRepository.save()` directly with an unset role.

**Conclusion: there is no live, reachable application code path today that persists a null-role row.** This is a defense-in-depth / DB-constraint gap, not a demonstrated live defect — the risk is (a) a direct DB manipulation, restore, or manual SQL outside the app, or (b) a future code path (e.g., a new admin bulk-import, a partial JPA merge that skips the role field, or a future write path added without the same defensive default) reintroducing it. Given the severity of the two failure modes if it ever does occur (broad-blast-radius 500 for mode 1, silent ADMIN-equivalent access for mode 2), hardening is still warranted, but the proposal phase should be explicit that this is preventive/defense-in-depth work, not a hotfix for an active incident.

## Affected Areas

- `backend/src/main/java/com/dh/dentalClinicMVC/entity/User.java` — `role` field (line 40, no `nullable = false`), `getAuthorities()` (lines 44-46, NPE source).
- `backend/src/main/java/com/dh/dentalClinicMVC/configuration/JwtAuthenticationFilter.java` — `doFilterInternal()` (lines 35-110), the uncovered NPE gap between the two existing catches.
- `backend/src/main/java/com/dh/dentalClinicMVC/configuration/ApplicationConfig.java` — `userDetailsService()` bean (lines 23-32), shared choke point between JWT-filter auth and login auth.
- `backend/src/main/java/com/dh/dentalClinicMVC/service/impl/AppointmentServiceImpl.java` — `findAllForCurrentUser()` (lines 205-222), the ADMIN-fallthrough `else` branch. This is the only role-dispatch-with-fallthrough pattern in the codebase — a full grep for `.getRole()`/`Role role` usages across `backend/src/main/java` found no sibling pattern in `PatientServiceImpl`/`DentistServiceImpl` (their role handling is write-path defaulting, not read-path privilege dispatch) or elsewhere.
- `backend/src/main/java/com/dh/dentalClinicMVC/controller/AppointmentController.java` — `findAll()` (lines 141-163): the `else` branch (non-`User` principal, e.g. `@WithMockUser` tests) already fails safe via a ternary defaulting to `PATIENT`, not directly affected, but calls `findAllForCurrentUser()` so shares its downstream risk.
- `backend/src/main/java/com/dh/dentalClinicMVC/exception/StalePrincipalException.java` and `GlobalExceptionHandler.java` (`handleStalePrincipal()`, lines 231-242) — candidate reuse target for the 401 response.
- `backend/src/main/java/com/dh/dentalClinicMVC/security/StalePrincipalEntryPoint.java` and its wiring in `SecurityConfiguration.java:64` — candidate reuse target for the filter-layer 401 response.
- `backend/src/main/resources/db/migration/V1__create_initial_schema.sql` — candidate for a new `V2` migration adding `NOT NULL` (flagged as an open scope question, not assumed in/out).
- Test gaps confirmed: `backend/src/test/java/com/dh/dentalClinicMVC/configuration/JwtAuthenticationFilterTest.java` has zero null-role coverage; `backend/src/test/java/com/dh/dentalClinicMVC/service/impl/AppointmentServiceImplTest.java` covers ADMIN/PATIENT/DENTIST/stale-principal cases for `findAllForCurrentUser()` but no null-role case.

## Approaches

1. **Filter/auth-layer null-role guard (single choke point), reusing 401 machinery** — Add an explicit `role == null` check either inside the shared `ApplicationConfig.userDetailsService()` lambda or in `JwtAuthenticationFilter.doFilterInternal()` right after `loadUserByUsername()` returns, before `isTokenValid`/`getAuthorities()` are invoked. Because `findAllForCurrentUser()` is only ever reached via an authenticated `SecurityContext`, this makes the null-role user fail auth before it can reach the service-layer dispatch at all — fixing mode 1 directly and making mode 2 unreachable via the normal request path.
   - Pros: single fix point; reuses existing, already-tested 401 response machinery (`StalePrincipalEntryPoint` for the filter path); smallest blast radius.
   - Cons: touches a bean shared with the login `DaoAuthenticationProvider` path — needs explicit design for whether login should also reject (plausibly should, and would get 401 "Credenciales inválidas" via existing `BadCredentialsException` translation, but that message is misleading for a data-integrity condition) or whether the guard should live only in the filter (leaving login's behavior for a null-role user technically unspecified/unchanged, arguably worse — an unusable-but-not-rejected account). Distinguishing "row missing" from "row exists but role invalid" cleanly likely needs a distinct exception type reusing the same 401 shape, not literal reuse of `StalePrincipalException` (its own doc comment scopes it to "no backing row").
   - Effort: Medium.
2. **Fix `findAllForCurrentUser()` fail-safe dispatch only** — change the `else` branch to require an explicit `Role.ADMIN` match and throw/deny otherwise, without touching the filter layer.
   - Pros: smallest, most localized change; directly closes the originally-scoped privilege-escalation gap; cheap defense-in-depth regardless of what else ships.
   - Cons: does not fix the filter-layer NPE (mode 1) at all — a null-role user would still get a 500 on every authenticated request, including ones that never reach this method. Insufficient as a standalone fix.
   - Effort: Low.
3. **DB-level hardening: `NOT NULL` constraint via new Flyway `V2` migration + `nullable = false` on `User.role`** — prevents the null state from ever being persisted.
   - Pros: closes the gap at the source; complements either app-layer approach as defense-in-depth.
   - Cons: is an actual schema change (new migration file), needs an explicit user/proposal decision to include; would need a backfill/assertion step (`UPDATE users SET role='PATIENT' WHERE role IS NULL` before adding the constraint) to be safe against any pre-existing out-of-band null rows, even though the reachability analysis found none possible from application code. Does not address application-layer behavior by itself.
   - Effort: Low-Medium, but carries an explicit scope decision.

## Recommendation

Combine Approach 1 (filter/auth-layer guard, the primary fix — addresses both failure modes by construction since it prevents a null-role principal from ever reaching an authenticated `SecurityContext`) with Approach 2 (fail-safe `findAllForCurrentUser()` dispatch, cheap belt-and-suspenders that also protects any future caller of that method that bypasses the filter). Approach 3 (DB `NOT NULL` migration) is worth strongly recommending as a genuine root-cause fix, but should be raised as an explicit proposal-time scope question rather than assumed in scope — it is the only approach requiring a schema change, and the reachability analysis shows it is not urgently required to close the two described failure modes (no live path creates the condition today), so it can reasonably be deferred to a follow-up if the user wants a strictly backend-code-only change this round.

For the 401 mechanics: recommend a new, narrowly-scoped exception type (not literal reuse of `StalePrincipalException`, whose own doc comment scopes it to "no backing row") that shares `GlobalExceptionHandler`'s `ErrorResponse` 401 shape via a new `@ExceptionHandler` method (for any controller/service-layer null-role detection) and a corresponding filter-layer null check that reuses the existing `StalePrincipalEntryPoint` (no new entry point needed). This keeps D2's 401 alignment while keeping the "row exists but role invalid" condition semantically distinct from "row missing" in code, which matters for logging/observability even though the wire response is uniform. This is proposal-phase-level detail; the exploration surfaces the two viable exception-reuse patterns (extend `StalePrincipalException`'s scope vs. add a sibling type) for the proposal to decide between.

## Risks

- Filter-layer NPE (mode 1) is broader blast radius than originally scoped: it breaks all authenticated endpoints for a null-role user (every `@PreAuthorize`-protected route), not just `GET /appointments`.
- The `ApplicationConfig.userDetailsService()` bean is shared between JWT-filter auth and username/password login (`DaoAuthenticationProvider`) — a naive fix in that shared lambda has login-path side effects (misleading "bad credentials" 401 message) that need an explicit design decision.
- No additional privilege-escalation-fallthrough call sites were found beyond the originally-scoped `AppointmentServiceImpl.findAllForCurrentUser()` — `PatientServiceImpl`/`DentistServiceImpl` have null-role handling but it's write-path defaulting, not read-path dispatch, so this task's scope for mode 2 does not need to expand.
- Reachability: no live code path in the current codebase can actually persist a null-role row (all write paths default it). This changes prioritization but not validity — hardening still protects against direct-DB-manipulation and future-code-path regressions given the severity if it did occur.
- `NOT NULL` migration (if pursued) needs a backfill/assertion step to be safe against any pre-existing out-of-band null rows in a live DB, even though none are expected from application code.
- Zero existing test coverage for the null-role case at either the filter (`JwtAuthenticationFilterTest`) or service (`AppointmentServiceImplTest`) layer — any fix needs new tests at both layers.

## Ready for Proposal

Yes. Current code state re-verified post-refactor (line numbers confirmed independently by the orchestrator), exact call sites confirmed, no additional privilege-escalation call sites found beyond the originally-scoped one, reachability assessed (theoretical/defense-in-depth, not a live bug), and the shared `UserDetailsService` bean risk surfaced as a new design consideration for `sdd-propose` to resolve. The DB `NOT NULL` migration should be explicitly raised as an in/out-of-scope question during proposal.
